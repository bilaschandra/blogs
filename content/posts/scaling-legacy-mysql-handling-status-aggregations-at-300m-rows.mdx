## Executive Summary

As applications mature over decades, database tables often swell to hundreds of millions of rows. When user interfaces demand real-time aggregations—such as live count summaries across different statuses in a project list view—legacy relational database engines like MySQL begin to choke under the weight of dynamic queries. 

This technical article explores a real-world engineering challenge: optimizing status count aggregations on a 15-year-old MySQL `projects` table containing over **300 million records**. We break down why conventional indexing strategies fail, analyze potential architectural patterns, and detail a pragmatic, phased migration plan—moving from a dual-cron batch reconciliation engine (short-term) to an event-driven Kafka architecture (long-term).

---

## 1. Problem Statement: The Scaling Wall at 300 Million Rows

### 1.1 Context & Schema History
Fifteen years ago, the core application schema was designed around a monolithic, highly normalized relational structure. The primary `projects` table (and associated `tasks` relational entities) was architected to handle tens of thousands of records per day. Today, the dataset exceeds **300,000,000 records**, occupying hundreds of gigabytes of disk space and pushing InnoDB memory buffers to their physical limits.

The core product requirement for the primary dashboard is a paginated **Project Data List Page**. Beside each project row (or project category filter), the frontend displays dynamic counter metrics indicating the breakdown of sub-items by status:
* `Draft`
* `Pending Approval`
* `In Progress`
* `Under Review`
* `Completed`
* `Archived`

```
+---------------------------------------------------------------------------------------------------+
| Project Name  | Total Tasks | Draft | In Progress | Review | Completed | Created Date | Actions   |
+---------------------------------------------------------------------------------------------------+
| Alpha Launch  |    1,420    |   12  |     300     |   8    |   1,100   | 2024-01-15   | [View]    |
| Beta Migration|   85,000    |  450  |   12,300    | 120    |  72,130   | 2023-11-02   | [View]    |
+---------------------------------------------------------------------------------------------------+
```

### 1.2 The Bottleneck: Index Degradation & Partial Index Matching
To generate these metrics dynamically on page render, the application historically executed queries containing `COUNT(*)` with `GROUP BY status` or multiple conditional `SUM(CASE WHEN status = 'X' THEN 1 ELSE 0 END)` subqueries.

```sql
-- Legacy Dynamic Aggregation Query
SELECT 
    project_id,
    COUNT(*) AS total_count,
    SUM(CASE WHEN status = 'DRAFT' THEN 1 ELSE 0 END) AS draft_count,
    SUM(CASE WHEN status = 'IN_PROGRESS' THEN 1 ELSE 0 END) AS in_progress_count,
    SUM(CASE WHEN status = 'COMPLETED' THEN 1 ELSE 0 END) AS completed_count
FROM project_tasks
WHERE organization_id = 1052
  AND is_deleted = 0
  AND created_at >= '2025-01-01'
GROUP BY project_id;
```

While composite secondary indexes exist (e.g., `INDEX (organization_id, is_deleted, status, created_at)`), performance has degraded severely due to several database mechanics:

1. **Partial Index Hits:** As product teams introduced new filtering criteria over the years (e.g., date ranges, assignee tags, tenant sub-types), queries frequently bypass the optimal composite index path. MySQL's optimizer falls back to range index scans or index intersection (`Using intersect(...)`), scanning millions of B+ tree leaf nodes per web request.
2. **Buffer Pool Thrashing:** Cold reads for random 300M+ row pointer lookups flush active pages out of the InnoDB Buffer Pool, inflating CPU load to 90%+ and spiking disk I/O wait times.
3. **Lock Contention:** Heavy write operations (thousands of status transitions per minute) lock rows and index pages, causing read query queues to back up and resulting in HTTP 504 Gateway Timeouts.

## 2. Problem Breakdown & Engineering Analysis

To formulate a resilient architecture, we must analyze the problem across three distinct layers:

```
+------------------------------------------------------------------------+
|                          PROBLEM BREAKDOWN                             |
+-----------------------------+------------------------------------------+
| Layer                       | Root Cause & Impact                      |
+-----------------------------+------------------------------------------+
| 1. Storage & Indexing       | High B+ Tree depth (4-5 levels), index    |
|                             | bloat, and poor selectivity on status.   |
+-----------------------------+------------------------------------------+
| 2. Query Execution          | OLTP engines (MySQL) are unsuited for    |
|                             | OLAP aggregation workloads over 300M rows|
+-----------------------------+------------------------------------------+
| 3. Domain Logic & State     | Non-linear status transitions (ping-pong |
|                             | state shifts like In Progress -> Draft). |
+-----------------------------+------------------------------------------+
```

### Key Technical Challenges:
* **Non-Linear State Transitions:** Tasks do not move monotonically from state A to B to C. Users frequently move items back and forth (e.g., `In Progress` $
ightarrow$ `Under Review` $
ightarrow$ `In Progress` $
ightarrow$ `Draft`). Simple increment/decrement logic must account for state rollbacks.
* **Write Saturation:** Any solution that updates count records synchronously inside the core user HTTP request path introduces severe transactional locks and tight coupling.
* **Data Consistency vs. Latency:** The UI requires low latencies (< 200ms page load), but sub-second hard consistency for count summaries is an unnecessary constraint for user experience. Eventual consistency is business-acceptable if managed within tight bounds.

Before selecting our implementation path, we evaluated four major architectural patterns:

| Architectural Approach | Pros | Cons | Feasibility for 300M+ Rows |
| :--- | :--- | :--- | :--- |
| **1. | **2. Key-Value Caching**<br />*(In-Memory Redis Counters)* | • Sub-millisecond reads.<br />• Reduces MySQL read load completely. | • Cache invalidation complexity.<br />• High risk of drift during node failures or network partitions.<br />• Cold start rebuilding is slow. | ⚠️ Partial Solution |

## 5. Phase 1: Short-Term Solution — Dual-Cron Batch Sync Engine

The short-term solution introduces a dedicated, highly optimized **Read-Model Counter Table** (`project_status_counts`) populated asynchronously via two complementary background cron jobs: a **Delta Sync Cron** and a **Reconciliation Cron**.

### 5.1 Schema Design for Pre-Aggregated Counts

```sql
CREATE TABLE project_status_counts (
    project_id BIGINT UNSIGNED NOT NULL,
    draft_count INT UNSIGNED NOT NULL DEFAULT 0,
    in_progress_count INT UNSIGNED NOT NULL DEFAULT 0,
    review_count INT UNSIGNED NOT NULL DEFAULT 0,
    completed_count INT UNSIGNED NOT NULL DEFAULT 0,
    archived_count INT UNSIGNED NOT NULL DEFAULT 0,
    total_count INT UNSIGNED NOT NULL DEFAULT 0,
    last_delta_synced_at DATETIME NOT NULL,
    last_reconciled_at DATETIME NOT NULL,
    PRIMARY KEY (project_id),
    KEY idx_last_delta (last_delta_synced_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 5.2 System Architecture: Dual-Cron Strategy

```
+----------------------------------------------------------------------------------+
|                            PHASE 1 ARCHITECTURE                                  |
|                                                                                  |
|  +--------------------+                                                          |
|  |  Main Projects /   |                                                          |
|  |  Tasks Table       |                                                          |
|  |  (300M+ Rows)      |                                                          |
|  +---------+----------+                                                          |
|            |                                                                     |
|            | (1) Read Delta Changes (updated_at >= T-35m)                        |
|            v                                                                     |
|  +--------------------+    (2) Upsert Aggregates    +-------------------------+  |
|  | 30-Min Delta Cron  | -------------------------> | project_status_counts   |  |
|  +--------------------+                            | (Pre-aggregated Table)  |  |
|                                                    +------------+------------+  |
|  +--------------------+                                         ^                |
|  |  Daily Full Sync   | ----------------------------------------+                |
|  |  Reconciliation    |    (3) Reconcile Drift & Inconsistencies                 |
|  |  Cron (Off-Peak)   |                                                          |
|  +--------------------+                                                          |
+----------------------------------------------------------------------------------+
```

#### 1. Delta Sync Cron (Runs Every 30 Minutes)
* **Goal:** Process only the subset of projects whose tasks underwent status changes in the last 30 minutes (with a 5-minute overlap window to handle clock drift/long transactions).
* **Strategy:**
  1. Fetch modified `project_id` values:
     ```sql
     SELECT DISTINCT project_id 
     FROM project_tasks 
     WHERE updated_at >= NOW() - INTERVAL 35 MINUTE;
     ```
  2. Compute exact status aggregates only for those specific `project_id`s.
  3. Execute bulk `UPSERT` (`INSERT ... ON DUPLICATE KEY UPDATE`) into `project_status_counts`.

#### 2. Reconciliation Cron (Runs Daily at Off-Peak Hours)
* **Goal:** Correct state drift, handle missing update events, and fix edge cases resulting from state transitions (e.g., tasks moving back and forth between `In Progress` and `Draft`).
* **Strategy:**
  1. Chunk projects by primary key ranges (`project_id BETWEEN X AND Y`) to avoid locking large table segments.
  2. Perform full aggregation calculations for each chunk.
  3. Overwrite pre-aggregated rows and update `last_reconciled_at`.

### 5.3 Handling State Fluctuations (The "Ping-Pong" Edge Case)

Consider a task moving: `Draft` $
ightarrow$ `In Progress` $
ightarrow$ `Draft` $
ightarrow$ `In Progress`.

Because the Delta Cron recomputes the **absolute count** for modified projects rather than using naive relative increments (`count = count + 1`), state resets naturally self-correct without accumulating math errors:

```sql
-- Re-calculating full row state for impacted projects ensures mathematical correctness
INSERT INTO project_status_counts (
    project_id, draft_count, in_progress_count, completed_count, total_count, last_delta_synced_at
)
SELECT 
    project_id,
    SUM(CASE WHEN status = 'DRAFT' THEN 1 ELSE 0 END),
    SUM(CASE WHEN status = 'IN_PROGRESS' THEN 1 ELSE 0 END),
    SUM(CASE WHEN status = 'COMPLETED' THEN 1 ELSE 0 END),
    COUNT(*),
    NOW()
FROM project_tasks
WHERE project_id IN (:impacted_project_ids)
GROUP BY project_id
ON DUPLICATE KEY UPDATE
    draft_count = VALUES(draft_count),
    in_progress_count = VALUES(in_progress_count),
    completed_count = VALUES(completed_count),
    total_count = VALUES(total_count),
    last_delta_synced_at = VALUES(last_delta_synced_at);
```

## 6. Phase 2: Long-Term Solution — Event-Driven Architecture via Apache Kafka

While Phase 1 reduces database read queries from minutes to milliseconds, it still relies on polling and batch aggregation. As data grows beyond 500M+ rows, Phase 2 replaces polling with an **Event-Driven CQRS Architecture**.

### 6.1 Event-Driven System Architecture

```
+---------------------------------------------------------------------------------------+
|                                PHASE 2 ARCHITECTURE                                   |
|                                                                                       |
|  +--------------------+            +-------------------+           +---------------+  |
|  | Application Service| --(Event)->| Apache Kafka      | --(Sub)-->| Counter Sync  |  |
|  | (Write Operations) |            | Topic:            |           | Consumer      |  |
|  +--------------------+            | task-status-events|           +-------+-------+  |
|                                    +-------------------+                   |          |
|                                                                            | Atomic   |
|                                                                            v Upsert   |
|  +--------------------+            +-------------------+           +---------------+  |
|  |  MySQL CDC         | --(CDC)--> | Kafka Connect     | --------> | Read Model    |  |
|  |  (Debezium Engine) |            | (Alternative Path)|           | (Redis/MySQL) |  |
|  +--------------------+            +-------------------+           +---------------+  |
+---------------------------------------------------------------------------------------+
```

### 6.2 Key Architectural Components

1. **Domain Event Publication:**
   When a user updates a task status, the Application Write Service publishes a structured JSON payload to the Kafka topic `task.status.changed`:
   ```json
   {
     "event_id": "evt_987654321",
     "event_type": "TASK_STATUS_CHANGED",
     "project_id": 1052,
     "task_id": 44012,
     "previous_status": "IN_PROGRESS",
     "new_status": "DRAFT",
     "timestamp": "2026-07-29T11:57:00Z"
   }
   ```

2. **Stream Processing & Counter Workers:**
   Kafka consumers consume messages partitioned by `project_id` (ensuring in-order event processing per project). 
   
   Upon receiving a state transition event (`IN_PROGRESS` $
ightarrow$ `DRAFT`), the worker executes an atomic counter delta update:
   ```sql
   UPDATE project_status_counts 
   SET in_progress_count = GREATEST(0, in_progress_count - 1),
       draft_count = draft_count + 1,
       updated_at = NOW()
   WHERE project_id = 1052;
   ```

3. **Change Data Capture (CDC) Alternative:**
   If modifying legacy application code to emit events is too risky, **Debezium CDC** can tail the MySQL binary log (`binlog`) and stream database row-level changes directly into Kafka without touching application code.

4. **Self-Healing Reconciliation:**
   The daily reconciliation cron from Phase 1 remains as a secondary fallback worker to audit and fix any rare event loss due to consumer failure or unhandled deserialization errors.

## 7. Migration & Rollout Strategy

To transition safely without impacting production uptime:

1. **Dual-Writing / Shadow Population:** Deploy the Phase 1 `project_status_counts` table and populate it via backfill script.
2. **Feature Flag Read Switch:** Introduce a feature toggle (`ENABLE_PREAGGREGATED_COUNTS`). Verify query speed gains in staging and production canary environments.
3. **Graceful Fallback:** If the pre-aggregated table lacks a row for a newly created project, fallback seamlessly to a targeted primary-key query.
4. **Deploy Phase 2 Kafka Event Pipeline:** Stream live updates alongside the Phase 1 crons until metrics confirm zero drift over a 30-day monitoring window.

---

## 8. Summary & Key Engineering Takeaways

1. **OLTP vs. OLAP Separation:** Relational databases like MySQL excel at single-row ACID transactions, but degrade rapidly when performing dynamic aggregations across 300M+ rows.
2. **Decouple Readers from Writers:** Pre-aggregating metrics isolates write-heavy OLTP operations from high-throughput read dashboards.
3. **Iterative Refactoring over Big Bang Rewrites:** Implementing a 30-minute dual-cron pre-aggregation model provides immediate operational relief while building towards a scalable Kafka event-driven architecture.
